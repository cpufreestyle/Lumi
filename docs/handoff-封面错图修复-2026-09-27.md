# 交接：歌曲封面「有时候会不对」修复（2026-09-27）

> **第二轮补充（同日）**：已加入磁盘缓存，并**推翻了「AppleScript 恒返回 0 字节」的结论**。
> 第一轮的根因分析仍有效，但其中「AppleScript 已死、每首歌必走在线源」的判断
> 是竞态窗口造成的误判，请以文末「第二轮」章节为准。

## 一句话

封面此前只能靠网易云「歌名+歌手」模糊匹配，同名同歌手的不同版本会张冠李戴；
现已改为**优先 Apple Music 官方目录**（同源即同图），并新增**专辑名 + 时长**
两路消歧，网易云降级为兜底，另加磁盘缓存。

## 现象

界面上的专辑封面偶尔是另一首歌 / 另一个版本的图。

## 根因（三层，逐层叠加）

### 1. AppleScript 取封面这条路在本机是死的

macOS 26 的 Music 关闭了 artwork 的 Apple event 读取。日志实测（修复前）：

```
封面诊断：descriptor type=1970567284 bytes=0 exists=ART
```

descriptor 有类型但 **0 字节**，且每首歌都如此。`type=1970567284` 即 `"data"`，
说明不是「封面还没就绪」，而是接口读不到。因此实际每一首歌的封面都来自
在线回退源，Apple 本地封面从未成功过。

### 2. 唯一的在线源无法区分「同名同歌手的不同版本」

原实现只有网易云一个源，评分只看歌名 + 歌手。而这正是版本歧义的典型场景：

| 版本 | 歌名 | 歌手 | 时长 | 专辑 |
|---|---|---|---|---|
| 录音室版 | 神预言 | 袁娅维 | 191.6s | 月亮失眠了 |
| Live 版 | 神预言 | 袁娅维 | 268.7s | 为歌而赞第二季 第12期 |

两者歌名歌手**一字不差**，评分完全相同，取到哪个取决于网易云接口的排序 ——
这就是「有时候对、有时候不对」的直接原因。实测该查询返回两个同分候选。

### 3. 兜底候选不过分数线

查询词用尽时，原实现直接返回「历史最高分」，哪怕只有 60 分（歌名互相包含、
歌手对不上）也会贴上去。网易云大量 Live / Acoustic / 翻唱条目正是这么混进来的。

## 已排除的方案（不要重复走）

| 方案 | 结论 |
|---|---|
| **Apple MusicKit API** | `server.js` 的 `/api/token` 依赖 `.env`，但里面是假样例值（`APPLE_TEAM_ID=ABC123DEF`、私钥只有一行 base64），调用报 `secretOrPrivateKey must be an asymmetric key when using ES256`。用户从未提供真实 `.p8`。 |
| **iTunes Search API（作为唯一源，本轮之前的判断）** | 早期测试用 `country=cn` **恒返回 0 条**，据此被判定为「中文命中率极差」。**这个结论是错的** —— 是店铺参数问题，不是覆盖问题。见下。 |
| **读本地音频文件内嵌封面** | 本机 Music 库是纯流媒体：`~/Music/Music/Media.localized/Music` 为空，且已无 `Item.db`（改用 `.musicdb` 新格式），无本地文件可读。 |
| **`asset location` AppleScript 属性** | 本机 Music 脚本字典不支持，取值报语法错误。 |

## 本轮改动

### 新增主源：Apple Music 官方目录

`fetchArtworkFromAppleCatalog()`（`MusicController.swift`）

- 走 iTunes Search API，返回的 `artworkUrl100` 就是 Apple Music 自己在用的那张图，
  **同源即同图**，命中时不存在取错版本的可能。
- 尺寸：URL 里把 `100x100bb` 替换成 `600x600bb`（同一 URL 模板，Apple 侧按尺寸出图）。
  实测 600×600 得 104,940 字节 JPEG，100×100 仅 5,559 字节。
- 店铺顺序 `["tw", "hk", "sg", "jp"]`，逐个试，第一个有结果的即采用。
  **关键发现**：`country=cn` 恒 0 条，但 tw/hk/sg/jp 对华语曲库覆盖都很好 ——
  这纠正了此前「iTunes 中文命中率极差」的错误判断。
- 命中判定：`bestAppleHit()` 四路交叉验证取最高分。

`ArtworkScoring`（新建，`Sources/Lumi/Modules/Music/Models/ArtworkScoring.swift`）

**必须做**：Apple 的 tw/hk 店铺返回繁体「神預言 袁婭維」，而 Music 报简体

1. **实机观感需用户肉眼确认**：部署时正在播《寂寞不痛》且曲目未变，封面链路
   未被触发（日志无新行）。下次切歌时看日志是否出现：
   ```

   ```
   若出现 `封面：Apple 目录未命中，退网易云`，说明该曲 Apple 未收录，已正确降级。

2. **`artworkAppleTried` 的语义**：`fetchArtworkFromAppleCatalog` 里有
   `guard !artworkAppleTried, !artworkNeteaseTried` 的双向互斥。若某首歌
   Apple 判死转网易云，网易云也失败，本曲就不再重试（保持占位图）。

   因为切歌时 `artworkAppleTried` 会被复位。若发现反复失败的曲目在重播时

3. **未加的优化**：封面结果没有落盘缓存，同一首歌每次切歌都要重新请求
   iTunes API。可考虑加 `~/Library/Application Support/Lumi/artwork_cache.json`
   （键 `歌名|歌手|专辑`，值 600×600 URL），参照已有的 `translation_cache.json`
   模式。这对本机尤其划算 —— AppleScript 已死，**每次切歌必然走网络**。

# 第二轮：磁盘缓存 + AppleScript 结论修正

## 1. 重要修正：AppleScript 并没有「死」

第一轮结论「macOS 26 关闭 artwork 读取，恒返回 0 字节」**是错的**，那是竞态窗口误判。

用源码同款脚本实测（当前曲目《刀马旦》）：

```
$ osascript -e 'tell application "Music" ... return data of artwork 1 of current track ...'
bytes=1197018        # 1.1MB，真实 JPEG
```

注意：`get count of (data of ...)` 这个写法**恒返回 0** —— AppleScript 对 data
类型求 count 得到的是元素个数，不是字节数，第一轮被这个坑误导过一次。
真正有效的判定是**按 `runScript` 返回的 descriptor 字节数**，源码里一直是对的。

所以实际链路是：

| 情况 | 行为 |
|---|---|
| 切歌瞬间（流媒体封面尚未就绪） | 返回 0 字节 → 连续两次判死 → 转在线源 |
| 封面就绪后 | 返回 1.1MB → **直接用官方原图**，零网络 |

`artworkScriptBlocked` 是切歌时**不复位**的（这个设计反而对了），主轮询每轮仍在探，
封面一旦就绪就能回到本地源。新增的磁盘缓存让这条竞态路径变得不重要 ——
首次取到后，后续重播不再依赖任何在线请求。

## 2. 新增：封面磁盘缓存

### 为什么需要

本机 AppleScript 在切歌瞬间经常 0 字节，一首歌可能要走
`AppleScript 2 次探测 → Apple 目录 4 个店铺 → 网易云 3 跳`，
**每次切歌都重来一遍**。用户单曲循环时尤其浪费。

### 设计

- **位置**：`~/Library/Caches/Lumi/artwork/<sha256(键)>.jpg`
  放 `Caches` 而非 `App Support` —— 可被系统清理，清理后只是重取一次图。
- **键**：`ArtworkScoring.cacheKey(title:artist:album:)` = 三字段归一化后拼接。
  **必须带专辑**：录音室版与 Live 版歌名歌手全同，少了专辑会互相顶掉。
  归一化含繁简统一，繁体店铺与简体 Music 落到同一文件。
- **文件名用 SHA256**：键含歌名/歌手/专辑，可能带斜杠、超长，哈希避开。
- **读**：切歌时同步读（`fetchInfoSync` 的 `trackChanged` 分支）。
  本地读一张 <200KB JPEG 远快于既有的 AppleScript 阻塞调用（100–300ms）。
  命中即 `hasArtFlag = true`，**跳过全部在线分支**。
- **写**：`installArtwork` 内缩放完成后写（在 artworkQueue 上）。
  写在代号核对**之前**是有意的 —— 即便已切歌，该图对缓存键仍正确，下次重播直接命中。
- **容量**：600 张上限，超了按 mtime 淘汰最旧。单张约 80–90KB → 上限 ≈ 50MB。

### 顺带修掉的糊图问题

原实现缩放到 **280×280**，而展示区最大 **240pt**（Retina 下需 480px），
等于用 140pt@2x 的图撑 240pt，放大必然发虚。现已改到 `artworkRenderSize = 640`。

### 关键防回归点

`fetchArtwork` 触发条件由
`(trackChanged && hasArt) || (!hasArtFlag && hasArt)`
改为 **`!hasArtFlag && hasArt`**。
否则缓存命中后 `hasArtFlag` 已为真，仍会因 `trackChanged && hasArt` 发起在线取图，
缓存白白失效，甚至被低置信度结果覆盖。

## 4. 第二轮遗留

1. **`artworkAppleTried` 的双向互斥**：`fetchArtworkFromAppleCatalog` 有
   `guard !artworkAppleTried, !artworkNeteaseTried`。某首歌两源都失败后本曲不再重试
   （保持占位图），但**重播会复位重试**。若发现某曲总是失败，可加按歌名的失败记忆。
2. **缓存无失效机制**：若某张图当时打分通过但事后发现是错的，需手动清
   `~/Library/Caches/Lumi/artwork/` 才能重取。目前没有 UI 入口。
3. **磁盘缓存绕过校验**：命中缓存时不重新跑 album/duration 复核。
   键里已含专辑，且写入时已过 115 分线，风险可控；要更严可在读取时用当前
   `queueAlbum`/`queueDuration` 再校验一次 `ArtworkScoring.score`。
4. **AppleScript 判死仍不可逆**：`artworkScriptBlocked` 一旦置真，切歌不再复位，
   后续曲目直接走在线源（即便其实读得到）。考虑磁盘缓存兜底，暂不改；
   要更稳可改成「连续 N 首失败才判死、每 N 首自愈一次」。
