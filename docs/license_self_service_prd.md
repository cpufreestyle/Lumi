# 功能规格（PRD）：激活码自助换发 + 设备绑定与吊销

> 版本：`v1.1`（规划中）　|　作者：产品 + 工程　|　状态：Draft　|　关联 release：v1.0.1（Ed25519 授权升级、旧码失效）

---

## 1. 问题陈述

v1.0.1 将激活码校验由 CRC16 升级为 **Ed25519 数字签名验签**，旧格式 `LUMI-XXXX-XXXX-XXXX-XXXX` 全部失效。已激活用户因本地授权持久化（`license.dat`）不受影响，但**重装 / 换机 / 清缓存**需重新激活时，旧码会被拒，只能人工邮件联系 `support@lumi.app` 换码。

由此产生三类成本：

- **客服成本**：每一次换码都是一封人工邮件往返，耗时以天计。
- **用户流失**：等待与操作摩擦导致部分用户放弃重新激活。
- **授权失控**：当前激活码无任何设备绑定与吊销机制，同一码可在任意设备无限激活，密钥一旦泄露只能整对更换。

不做此功能，v1.0.1 的授权升级虽安全，却把"迁移摩擦"和"分享漏洞"两个老问题留给了用户与运营。

---

## 2. 目标

| 维度 | 目标（可衡量） |
|---|---|
| 用户 | 旧码用户在 **5 分钟内自助**完成换发，无需等待客服 |
| 业务 | 换码相关客服工单 **下降 ≥ 80%** |
| 安全 | 激活码可**绑定设备**、可被**吊销**，显著降低盗版分享面 |
| 兼容 | 新机制不破坏已发 `LUMI1-` 码的正常运行，平滑并存 |

**成功判断**：上线 30 天内，自助换码完成率 ≥ 90%、换码工单下降 ≥ 80%、设备绑定覆盖 ≥ 95% 的新激活。

---

## 3. 非目标（明确不做）

- **不做完整账号体系**：不引入注册 / 登录 / 密码。换码仍以"旧码 + 订单号"为凭证，保持轻量。
- **不做实时在线校验**：维持**离线优先**设计（App 启动、日常使用不依赖网络），仅"换码"与"吊销清单"两处在线。
- **不做订阅计费**：本期仅覆盖一次性授权，不涉及按期续费扣款流程（到期提醒已独立规划）。
- **不重写 Ed25519 体系**：沿用 v1.0.1 的公钥内嵌 + 私钥仅存 `license-tool` 的架构。
- **不做跨设备云同步**：授权与设置同步（iCloud）属另一议题，不在本期。

---

## 4. 用户故事

1. **作为旧码用户**，我希望输入旧码和订单号就能自助换取新码，以便尽快恢复功能、不必等客服邮件。
2. **作为换机用户**，我希望在新设备上重新换发激活码（绑定新设备），而不必找人工，且旧设备上的授权自动失效。
3. **作为运营/作者**，我希望能吊销某个被盗或泄露的激活码，以便在密钥未整体泄露时止损。
4. **作为用户**，我希望换码过程每一步都有清晰反馈，失败时明确告知原因（旧码无效 / 订单号不匹配 / 已达设备上限）。
5. **作为付费用户**，我希望激活码绑定我的设备数量有合理上限（如 2–3 台），既能多设备使用又不会被无限分享。

## 5. 需求

### 5.1 自助换码（P0 — Must）

**行为**
- App「许可证」面板新增「旧码换发」入口，表单含：旧激活码、订单号（购买凭证）。
- 提交时客户端调用在线端点 `POST /v1/redeem`，携带：旧码、订单号、本机 `deviceId`、随机 `nonce`（防重放）。
- **服务端**逻辑（仅在换码环节参与，且私钥永不出服务端）：
  1. 用 v1.0.1 之前的 CRC16 旧校验逻辑（仅服务端保留实现）验证旧码格式/校验和合法；
  2. 校验订单号（见 Open Questions Q1，初期可用订单白名单或支付回调校验）；
  3. 校验该订单累计已签发的设备数 < 上限 `N`；
  4. 用私钥签发绑定当前 `deviceId` 的新激活码（见 5.2 的 `LUMI2-` payload）返回。
- 客户端收到后用内嵌公钥验签，验签通过即激活并持久化。

**验收标准**
- [x] 给定合法旧码 + 合法订单号 + 未达设备上限 → 返回可被内嵌公钥验签的新码，App 激活成功。
- [x] 旧码格式非法 / 校验和错误 → 返回明确错误「旧激活码无效」，不签发。
- [x] 订单号不匹配 → 返回「订单号与激活码不匹配」，不签发。
- [x] 同一订单已达设备上限 `N` → 返回「已达设备上限，请联系客服」，不签发。
- [x] 同一 `nonce` 重复使用（重放）→ 服务端拒绝，不重复签发。
- [x] 网络不可用时，客户端给出「换码需联网，请检查网络」而非静默失败。
- [x] 服务端私钥不参与 App 打包；换码响应仅含已签名的新码，不含任何私钥信息。

### 5.2 设备绑定（P0 — Must）

**Payload 演进**
新激活码采用前缀 **`LUMI2-`**，payload JSON 扩展：
```json
{ "v": 2, "life": false, "exp": 1798765432,
  "n": "<随机串>", "dev": "<deviceId>", "seq": 1 }
```
- `dev`：本机设备标识，由私钥签名，客户端无法篡改。
- `seq`：该订单下第几台设备（便于上限计数与用户感知）。
- 既有 `LUMI1-`（无 `dev`）继续被 `LicenseManager` 接受，保证兼容。

**客户端校验**
- `LicenseManager.validateLicenseKey` 增加分支：若 payload 含 `dev`，必须与本机 `deviceId` 相等，否则按 `.deviceMismatch` 失败并提示「该激活码已绑定其他设备，请换发」。
- `deviceId` 生成：取系统稳定标识（如 `IOKit` 平台 UUID 或 ` IOPlatformUUID`）散列，存入 **Keychain**，避免重装后变化。

**验收标准**
- [ ] 绑定的激活码在签发设备上激活成功；复制到另一台设备激活 → 失败并提示换发。
- [ ] 重装 App（不换机）后 `deviceId` 不变，授权仍有效。
- [ ] `LUMI1-` 旧码在已激活设备上不受影响（兼容路径）。

### 5.3 激活码吊销（P1 — Should）

**机制（离线优先的折中，诚实说明限制）**
纯离线 Ed25519 验签**无法实时吊销**（客户端无服务端状态）。采用「**签名吊销清单**」折中：
- 服务端维护吊销集合（被吊销激活码的 `n`/序列号），用同一私钥签名后发布到 `GET /v1/revocations`。
- 客户端在**有网络时**（启动或定时）拉取清单，用内嵌公钥验签后缓存到本地。
- 激活校验时若当前码的 `n` 命中清单 → 授权失效，提示「该激活码已被吊销，请联系客服」。
- **限制**：离线期间吊销有延迟，下次联网才生效；这是离线优先架构的固有取舍，需在隐私/安全说明中告知用户。

**验收标准**
- [ ] 服务端吊销某 `n` 后，该码在客户端下次联网时被识别为失效。
- [ ] 吊销清单本身经公钥验签，篡改无效。
- [ ] 清单为空/拉取失败时，不影响正常授权（不误杀）。

### 5.4 反馈与可观测（P1 — Should）
- [x] 许可证面板对「激活成功 / 失败原因 / 临期 / 已绑定设备数」给出显性状态，而非纯文本。
- [x] 客户端埋点（本地即可）：换码成功率、失败原因分布、设备绑定覆盖率，供后续量化目标（实现于 `Core/Telemetry.swift`，面板底部「本地诊断数据」折叠展示，仅存 UserDefaults 不上报）。

## 8. 时间与分阶段

- **阶段一（P0，建议 v1.1）**：自助换码 + 设备绑定（`LUMI2-` + `dev` 字段）。闭环 v1.0.1 迁移，落地设备限制。
- **阶段二（P1，建议 v1.1.x）**：吊销清单 + 面板反馈/埋点。
- 硬依赖：Q1（订单校验方案）须在阶段一开工前定稿；其余可在实现中收敛。
- 建议 phasing：先上线自助换码（哪怕设备上限先设宽松），快速消灭客服工单，再补吊销。

## 9. 安全设计要点（工程参考）

- **私钥边界**：换码签名、吊销清单签名均在服务端 `license-tool`（或等价服务端组件）完成；私钥仅存服务端/密钥管理，绝不在 App 二进制或换码响应中出现。
- **防重放**：换码请求带 `nonce` + 服务端去重（Q4）；吊销清单带 `issuedAt` 时间戳，客户端比对新鲜度。
- **deviceId 抗篡改**：`dev` 由私钥签名进 payload，客户端仅校验「本机 Keychain 中的 deviceId == payload.dev」，无法伪造。
- **兼容不降级**：`LUMI1-` 路径保留，旧码用户不强制升级；新码默认 `LUMI2-`。
- **吊销局限性透明化**：在隐私/授权说明中告知用户「吊销在下次联网生效」，避免安全错觉。
